## Step 84-post-triage — "wiped DB" was a divide-by-zero on a 100%-LOI material (2026-07-17)

High-priority bug: the team reported a **wiped database**. Triage on their copy (`mercy_triage_import.db`) proved the data was fully intact (52 employees, 167 parts, 19 mixtures, …) — the "wipe" was an **uncaught `ZeroDivisionError` failing loud** on open, exactly as Matthew read from the trace. Root cause in [`records/products.py`](records/products.py) `Mixture.getProp(prop, LOI=True)`: the ignited-basis oxide term `pct * matVal / (1 - matLOI/100)` divides by exactly 0 when a component material has **LOI = 100 %**. That is *legitimate data* — the fully-combustible organic binders **"PVA - Dry (Polyvinyl Alcohol)"** and **"Lard Oil"** burn off completely, so they carry LOI 100 and all-zero oxides → `0.0 / 0.0`. The real shop mixtures "Mold Mend P" / "Mold Mend P Max" contain PVA.

Why it read as a wipe: `getProp` on the LOI basis is called by `_refreshAllTabs() → mixturesTab.refreshTable()` (the Mixtures tab's oxide columns) on **every DB open, every edit, and the startup auto-reopen**. The uncaught error propagated straight out of `MainWindow.open()/_loadPath()`, so the window never finished rendering — an empty shell that looks like all the data vanished, and (via last-DB auto-reopen) crashes on every relaunch. Same crash also hit the Mixtures detail window and the **Mix Report** (`report/products.py`).

Fix (one line, one chokepoint — all three surfaces route through `getProp`): clamp the LOI fraction below 1, `loiFrac = min(max(matLOI/100, 0.0), 0.999)`, mirroring [`scheduling.requiredPressed`](scheduling.py)'s scrap clamp. **Provably changes no good data**: every material with LOI ≤ 99.9 has `min(max(LOI/100,0),0.999) == LOI/100` exactly, and the only LOI > 99.9 materials in the data (PVA, Lard Oil) carry zero oxides → a 0 term either way. Per the dual mandate, the truly impossible case (oxides present *and* LOI 100) now yields an absurd-but-finite, visibly-wrong number instead of a crash.

Defense-in-depth (team ask): the Materials editor ([`materials_tab.py`](materials_tab.py) `readData`) now **rejects the impossible entry at the source** — LOI ≥ 100 % with any non-zero oxide — with a clear message, following the existing per-field `errors` pattern (so Create stays live per the create-in-edit convention). Scoped to the *contradiction only*: a fully-volatile binder (LOI 100 %, all-zero oxides) still saves, and no legitimate material is rejected. Deliberately **not** a broad "chem sums to ~100 %" check — that needs a tolerance band and would false-positive on legitimate partial analyses.

Follow-up (same-day, second commit): closed the flagged sibling — `getCost`/`getProp` divide by the total batch weight, so a **zero-total-weight mixture** was the same latent render-crash. The mixture editor already requires positive component weights (`readData`'s "pos" check) and ≥1 material, so it's only reachable via legacy/hand-edited data; both methods now return `0` for a non-positive total weight (finite, non-crashing, and it can't propagate `None` into `Part.getMixCost`). No editor change needed — the entry path was already airtight.

Smoke **72 → 75**: `mixture_full_loi_material` pins all four getProp surfaces (finite + correct, Mixtures tab render, Mix Report, the LOI-99.0 no-perturbation control, impossible-data-stays-finite); `materials_impossible_loi_rejected` pins the editor guard (impossible combo rejected + not stored + error names LOI; valid binder accepted); `mixture_zero_weight_no_crash` pins the batch-weight backstop (getCost/getProp/​tab-render on a directly-built degenerate mixture, plus the empty-mixture control). All three verified to fail loudly with their fix reverted (16, 3, and 5 clean errors).
