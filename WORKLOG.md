## Bugfixes from the web port's employee audit (2026-10-21)

Four bugs found by the mercy-web session while it audited the eight employee tables for its port (its ROADMAP R15), and a fifth found while checking what the app does when its loader refuses a file. Each lands as its own commit with a smoke check that was run and seen to fail before the fix. Unreleased past `v2.0rc5`. Manual check: passed for all five (Matthew, on Windows, 2026-10-21, from two fuzz-based check files).

- **PTO carryover with less than 1 unused hour** ([pto_tab.py](pto_tab.py) `PTOCarryWindow`). The hours slider's minimum is 1, so with no unused hours last year Qt collapsed its range to 0..0 and Carry Over / Cash Out / Drop stored a 0-hour row, which the loader (`EmployeePTORange.setHours`, hours > 0) refuses: the saved file would not reopen. The three buttons now check the slider first and, below 1 hour, say there is nothing to carry over, cash out or drop, store nothing and close. Smoke `pto_carry_no_unused_hours` (all three buttons wrote `(today, marker, 0)` before the fix; a Drop for a tenured employee still writes; the saved file reloads).
- **An observance of a holiday the office added** ([records/employees.py](records/employees.py) `HolidayObservance.setHoliday`). The Defaults tab lets the office add and rename holidays, but `setHoliday` refused any name outside `defaults.HOLIDAYS`, so the first observance selected for such a holiday made the saved file refuse to load. It now accepts any name. Deliberately not "any name in the `holidays` table": an observance keeps its old name when its holiday is renamed or deleted on Defaults, and such files load today. Smoke `holiday_observance_custom_name_roundtrip` (create "Juneteenth", select an observance, rename it, select another under the new name, save, reload; the reload raised `holiday not in defaults.HOLIDAYS` before the fix).
- **Clearing one year's carryover cleared other years' too** ([records/employees.py](records/employees.py) `EmployeePTODB.clearCarry`). Its test `year and CARRY or CASH or DROP` bound as `(year and CARRY) or CASH or DROP`, so Manage Carryover → Reset, or overwriting this year's choice, also deleted every past year's CASH and DROP rows. Hours were unaffected (a past CASH/DROP adds 0 either way); the record of the choice was lost. The marker test is now `in ["CARRY", "CASH", "DROP"]`, grouped under the year. Smoke `pto_clear_carry_year_scoped` (records-level; before the fix, clearing 2026 also took a 2024 CASH and a 2025 DROP).
- **Editing an Other point stored the word "Other"** ([points_tab.py](points_tab.py) `PointsEditWindow.readData`). The create path stored the typed reason, but the update path stored the combo box's text, so any edit of an Other point (even of its value only) replaced the typed reason with "Other". Both paths now store the typed text. Lost reasons are not recoverable from the file: the office's file of 10-5-26 has 2 attendance rows whose reason is the word "Other" (recounted on a read-only copy, 2026-10-21; the same copy has no 0-hour PTO row and no holiday name outside `defaults.HOLIDAYS`, so the first two bugs had not reached it). Smoke `points_edit_keeps_other_reason` (before the fix, a value-only edit stored `'Other'`).
- **A file the loader refused was left open half-loaded, and Save then deleted what was not loaded** ([app.py](app.py) `MainWindow._loadPath`). When `_loadIntoDb` raised on a row (any `fromTuple` check), the exception escaped with the file manager already pointed at the new file and `self.db` partly filled. File → Open showed no message box and left Open / Save / Save As greyed out; the startup auto-reopen logged it and showed empty tabs. Both left the close prompt, whose default is Save, ready to write the partial `db`, and `saveFile` deletes every row not in memory: on fuzz copies with one planted 0-hour PTO row, notes, holidays, observances, production and orders (every table loaded after PTO) went to 0, and the bad row went too, so the file then opened normally with that data gone. `_loadPath` now catches the failure, closes the file without saving (new `FileManager.closeFile`), empties `db`, repaints, and shows an error box naming the file and the loader's message; nothing is left that Save could write over. A file that was open before is not reopened: as on a successful Open, its connection is already closed and its unsaved changes are gone either way. Not done: naming the table and row in the box (the recorded fix direction), since that means touching each of the loader's 28 table loops in a frozen file; the message plus the file let Matthew find the row from source. Smoke `load_refused_row_leaves_no_file_open` (File → Open over a good open file, and the auto-reopen path; before the fix, 10 failures, including closing with Save taking holidays 10 → 0, observances 60 → 0 and orders 4 → 0).

## T1.7 — tab-usage telemetry (2026-09-04)

The freeze's one sanctioned add (see the Freeze entry below): passive screen-usage logging feeding the web transition's Phase 4 screen triage — with no on-site observation possible, weeks of measured tab usage stand in for watching the office work. New root [`telemetry.py`](telemetry.py); `main.py` calls `telemetry.instrument(window)` after construction, which hooks `currentChanged` on every `QTabWidget` via `findChildren` and appends one JSONL line per activation — timestamp, hostname, app version, full breadcrumb (`Products/Mixtures`, computed by climbing ancestor QTabWidgets) — plus a `launch` marker per session, to `%LOCALAPPDATA%\MERCY\telemetry\usage-<hostname>.jsonl` (`MERCY_TELEMETRY_DIR` overrides; collection stays manual — the office sends the files at triage time).

Two deliberate guardrails: **screens, not work** (no record data, no field contents, no per-employee anything — decision 5's promise), and the one sanctioned inversion of the loud-failure mandate: telemetry can never crash or surface an error — any write problem silently drops the event. Because instrumentation lives in `main.py`, smoke's directly-constructed windows stay uninstrumented; the new check opts in explicitly. Smoke **76 → 77** (`telemetry_capture`: breadcrumb assertions for a top-level and a nested switch, plus a shadowed-log-dir probe proving `logEvent` swallows failures).

## Step 85 — machine-enforce the single-source facts (2026-07-20)

The single-source rule was a convention you had to **remember**; it's now a check.

New [`smoke/docs.py`](smoke/docs.py) → `docs_single_source`, text-only (no app imports, ~1 ms, runs second after `compile_all`), asserting three things:

1. **The Cursor's smoke baseline == `len(smoke.CHECKS)`.** Adding a check without updating HANDOFF — or vice versa — now fails loudly, naming both numbers.
2. **No other live doc restates the count.** Root `*.md` minus HANDOFF (the owner) and minus **WORKLOG, deliberately exempt** — its per-step counts are frozen history and are *correct* precisely because they don't track the live number. Also fails if HANDOFF itself states a count twice.
3. **Nothing shipped is still listed as planned** — no step number carries both a WORKLOG `## Step N` entry and a ROADMAP `### Step N` entry. This machine-checks the landing-commit lifecycle from HANDOFF § The doc system, and it keys off *headings* rather than the Cursor's prose, so rewording the Cursor can't spuriously redden smoke. One-directional (WORKLOG ⇒ not in ROADMAP), so the WORKLOG rotation rule stays safe.

The enabling refactor: the ordered check registry moved out of [`smoke/__main__.py`](smoke/__main__.py) into `CHECKS` in [`smoke/__init__.py`](smoke/__init__.py), so **a new check is registered in one place, not two** (the old dispatcher restated all 75 names — its own instance of the bug this step is about, and the exact chore CONVENTIONS called out for every migration bump). `__main__` is now a 12-line loop over `CHECKS`, and `__all__` gained `"CHECKS"` + the new name. That list is also what makes assertion 1 possible: there was previously no machine-readable count to compare against.

Smoke **75 → 76**. All five failure modes were verified to fire against monkeypatched doc contents (wrong count, missing baseline row, count stated twice, another doc restating it, shipped-and-planned overlap) — a doc check that can't fail is worse than no check, since it reads as coverage.

## Step 84-post-triage — "wiped DB" was a divide-by-zero on a 100%-LOI material (2026-07-17)

High-priority bug: the team reported a **wiped database**. Triage on their copy (`mercy_triage_import.db`) proved the data was fully intact (52 employees, 167 parts, 19 mixtures, …) — the "wipe" was an **uncaught `ZeroDivisionError` failing loud** on open, exactly as Matthew read from the trace. Root cause in [`records/products.py`](records/products.py) `Mixture.getProp(prop, LOI=True)`: the ignited-basis oxide term `pct * matVal / (1 - matLOI/100)` divides by exactly 0 when a component material has **LOI = 100 %**. That is *legitimate data* — the fully-combustible organic binders **"PVA - Dry (Polyvinyl Alcohol)"** and **"Lard Oil"** burn off completely, so they carry LOI 100 and all-zero oxides → `0.0 / 0.0`. The real shop mixtures "Mold Mend P" / "Mold Mend P Max" contain PVA.

Why it read as a wipe: `getProp` on the LOI basis is called by `_refreshAllTabs() → mixturesTab.refreshTable()` (the Mixtures tab's oxide columns) on **every DB open, every edit, and the startup auto-reopen**. The uncaught error propagated straight out of `MainWindow.open()/_loadPath()`, so the window never finished rendering — an empty shell that looks like all the data vanished, and (via last-DB auto-reopen) crashes on every relaunch. Same crash also hit the Mixtures detail window and the **Mix Report** (`report/products.py`).

Fix (one line, one chokepoint — all three surfaces route through `getProp`): clamp the LOI fraction below 1, `loiFrac = min(max(matLOI/100, 0.0), 0.999)`, mirroring [`scheduling.requiredPressed`](scheduling.py)'s scrap clamp. **Provably changes no good data**: every material with LOI ≤ 99.9 has `min(max(LOI/100,0),0.999) == LOI/100` exactly, and the only LOI > 99.9 materials in the data (PVA, Lard Oil) carry zero oxides → a 0 term either way. Per the dual mandate, the truly impossible case (oxides present *and* LOI 100) now yields an absurd-but-finite, visibly-wrong number instead of a crash.

Defense-in-depth (team ask): the Materials editor ([`materials_tab.py`](materials_tab.py) `readData`) now **rejects the impossible entry at the source** — LOI ≥ 100 % with any non-zero oxide — with a clear message, following the existing per-field `errors` pattern (so Create stays live per the create-in-edit convention). Scoped to the *contradiction only*: a fully-volatile binder (LOI 100 %, all-zero oxides) still saves, and no legitimate material is rejected. Deliberately **not** a broad "chem sums to ~100 %" check — that needs a tolerance band and would false-positive on legitimate partial analyses.

Follow-up (same-day, second commit): closed the flagged sibling — `getCost`/`getProp` divide by the total batch weight, so a **zero-total-weight mixture** was the same latent render-crash. The mixture editor already requires positive component weights (`readData`'s "pos" check) and ≥1 material, so it's only reachable via legacy/hand-edited data; both methods now return `0` for a non-positive total weight (finite, non-crashing, and it can't propagate `None` into `Part.getMixCost`). No editor change needed — the entry path was already airtight.

Smoke **72 → 75**: `mixture_full_loi_material` pins all four getProp surfaces (finite + correct, Mixtures tab render, Mix Report, the LOI-99.0 no-perturbation control, impossible-data-stays-finite); `materials_impossible_loi_rejected` pins the editor guard (impossible combo rejected + not stored + error names LOI; valid binder accepted); `mixture_zero_weight_no_crash` pins the batch-weight backstop (getCost/getProp/​tab-render on a directly-built degenerate mixture, plus the empty-mixture control). All three verified to fail loudly with their fix reverted (16, 3, and 5 clean errors).

## Step 80 — scheduler consumes `Press.currentPart` as the die-hysteresis seed (2026-07-15)

Algorithm restructured from a per-order horizon walk to a **time-outer walk** so a persistent `mount: press→part` map evolves in time order. Cost rule: free on your die's press; `dieChangeHours` charged only to displace a *different* resident die; a part with a home press but no free lane **defers** rather than hop. At the default `dieChangeHours = 0.0` the mount map is pure hysteresis — zero effect on completion dates. Input-only: `schedule()` never writes `currentPart` back. **⚠ The real-floor gate is UNMET** (Cursor carried-item): drills ran on synthesized/manually-entered mounts, not floor state. Full essay: archive §13.49.
